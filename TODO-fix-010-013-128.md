## Map 013 - 188 remaining diffs

Breakdown:
- **165 cells**: `actual=$025` (TILE_EMPTY) - our expander writes nothing, fixture expects ghost-house background tiles (`$0a0`-`$0c6` range)
- **23 cells**: Wrong tile written (various `$1aa`, `$1e2`, `$03f`, `$10b` etc.)

### The 165 empty cells (ghost-house background)

Affected area: rows 11-26, cols 1-15 (screen 0 interior) - the ghost house wall and floor pattern tiles.

**Investigation:** All 41 L1 objects in level 013 were expanded individually. None of them write to any of the 165 affected positions. The expected tile IDs (`$0a4`, `$0a5`, `$0a9`, `$0a8`, `$0b4`...) match the pattern data from `DATA_0DEADE` (lines 7790-7808 in bank_0D.asm), which is consumed by `CODE_0DEB6A` (extended handler index `$80`).

**Root cause:** Level 013's L1 object stream contains no extended object `$80`. The ghost house background is an automatic initialization that the game performs for ghost house levels, separate from the L1 object stream. It is triggered by the preset L2 mechanism (level 013's L2 pointer has bank=`$FF`, addr=`$EF80`, which maps to `$0DEF80` in bank `$0D`). The preset L2 initialization (`CODE_058126` in bank_05.asm, called when L2 bank=`$FF`) runs `CODE_0DEB6A` indirectly as part of the background setup.

Alternatively, the ghost house wall/floor tiles may be placed by a separate game-engine init that fires for tileset-5 levels. Either way, this is NOT addressable by static L1 object expansion.

**No handler fix is possible** without modeling the game engine's tileset-specific background initialization, which would require tracking the preset L2 subroutine execution path.

### The 23 wrong-tile cells

These cells have the wrong tile (not empty, but wrong value). They all come from object `[2] STD objNo=$12 settings=$71 pos=(18,16)` (a `handle_0DAB3E` call). The expected tiles are ghost house slope/wall tiles (`$0bf`, `$0af`, `$0ab`, etc.) but our handler produces arch/pipe pattern tiles (`$1aa`, `$1e2`, `$03f`).

**Likely cause:** `handle_0DAB3E` (CODE_0DAB3E) is a tileset-0 handler that produces different tiles than what tileset-5 expects for object $12. The tileset-5 dispatcher for object $12 (index 11, 0-based) routes to `CODE_0DA8C3` (the simple rectangular fill), not `CODE_0DAB3E`. The tileset dispatch should be routing these correctly via the ROM pointer tables, but it's possible `handle_0DAB3E` has a tileset-5 variant that's not being used, or the handler produces wrong tiles for tileset 5's object $12 interpretation.

This would require reading `CODE_0DA8C3`'s tile table for object $12 in tileset-5 vs what `CODE_0DAB3E` produces to diagnose the exact mismatch.

**Not investigated further** in this branch due to the iteration limit.
